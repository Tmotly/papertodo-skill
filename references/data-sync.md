# 外部编辑工作区数据文件：热重载与三方合并

仅当用户明确授权直接编辑 PaperTodo 工作区数据文件时使用。常规内容修改继续走 `create_*` / `add_todos` / `update_todo` / `write_note` 等领域工具。

## 背景规则

- 正常自动保存不会主动检测外部文件修改；显式热重载会阻止过期异步写入回流。
- `reload_data` 会用磁盘文件替换正在运行的内存状态，**尚未保存的内存修改会被覆盖**，执行前必须让用户知情。
- 没有文件监听，也没有自动合并；所有外部编辑都必须以显式重载或显式合并收尾。

## 直接编辑（以磁盘版本为准）

1. `get_data_reload_status` 读取 `WorkspaceNumber`、`DataFileName` 与 `IsReloading`。
2. 轮询等待 `IsReloading=false` 后再动文件。
3. 只编辑步骤 1 返回的那个工作区文件。**不要默认写主 `data.json`**；工作区号与数据文件名以状态返回为准。
4. 编辑时保持 JSON 结构与字段不变，只改目标内容。
5. 写完后 `reload_data()` 让 PaperTodo 接受该文件。
6. 再查一次 `get_data_reload_status` 确认重载结果，然后把结果告知用户。

## 三方合并（保留双方独立修改）

1. 编辑前，把实际读取到的**完整原始 JSON** 原样保存在上下文里，作为 `baseline_json`。
2. 外部编辑完成后调用 `merge_data(baseline_json=<原始JSON字符串>)`。
3. 绝不能用修改后的文件、或后续重新保存的版本替代原始基线；不真实或缺失的基线必须拒绝合并。
4. 若只想直接采用磁盘版本，改调 `reload_data`，不要伪造基线去走合并。
5. 冲突处理：默认逐项询问用户。当前设置允许"只对冲突采用外部优先/内部优先"时按该策略，但不要为了免去询问而临时修改用户策略。
6. 合并后再查 `get_data_reload_status` 确认最终状态。

## 禁止事项

- 权限不足或 MCP 连接失败时说明原因，不改数据文件或插件私有数据。
- 不开启任何自动文件监听。
- 不把外部编辑当作绕过 `full` / `direct-delete` 权限的手段。
